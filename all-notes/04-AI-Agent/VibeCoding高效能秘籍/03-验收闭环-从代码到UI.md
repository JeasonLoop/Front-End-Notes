# 验收闭环：从代码到 UI

> 对应课程第三章。核心原则：**能被机器自动感知并拦下的错误，就永远不该消耗你的注意力。**

## 1. 先治过度设计：给 AI 做减法

Agent 是第二系统效应（Brooks《人月神话》）拉满的存在：生成代码边际成本为零，训练又让它倾向"考虑周全"，默认产出永远是加法做到底的版本，绝不会说"这个功能不该做"。

做减法三板斧：

1. **派活时就要求最小实现**："用最简单的方式实现，不要考虑本次需求之外的扩展性，能用现有依赖就不要造轮子。"
2. **事后让它自己做减法**："这段实现里，哪些代码可以删掉？哪些抽象是本次需求用不到的？"（作者实测一轮减法代码量少一半。）
3. **规则固化进 CLAUDE.md**："优先使用项目现有工具函数和依赖""不要为单一实现引入接口抽象"。

旧时代"提前做好抽象避免日后重构"的前提已不成立——现在 AI 重构成本趋近于零。**等需求真的出现再重构。**

## 2. 机器可验证闭环 + hooks

流水线从低到高：**typecheck → lint → 单元测试 → build → e2e**。错误越晚被发现修复代价越高。有了闭环，Agent 每改一轮自己收机器反馈、自己修，错误消化在它的循环内部。

规则（CLAUDE.md）是软约束，验证必须用 **hooks** 保证必然执行。两层推荐配置：

- **编辑后自动 lint**（PostToolUse hook）：`exit 2` 把 stderr 报错回灌给模型，它看到报错自己修。
- **新功能完成后强制 build + e2e**：指令固定"build 和 e2e 都绿才算做完"。

### Checklist：验收的核心是清单，工具只是执行器

工具各验一个维度，"这次产出合不合格"是综合判断。把标准写成显式 checklist 放进 CLAUDE.md，例如：

- 不要出现超过 500 行的模块，超了必须拆
- 不要用 emoji 当图标，一律用项目的 icon 组件
- 不要新增重复的工具函数，写之前先搜一遍现有代码
- 不要吞错误的空 catch，要么处理要么往上抛
- 涉及用户输入的地方必须考虑 XSS

清单是长出来的：起手写五六条最在意的，每次翻车往里沉淀一条。

### 验收标准前置

任务级验收标准：人给核心目标，**让 Agent 动手前先生成可执行的验收标准**（覆盖正常流程、空数据、失败处理、视觉检查），实现后沿同一份标准自己跑、自己核对、失败自己打回重改。验收越能被机器执行，Agent 自治程度越高。

## 3. 给 Agent 装上眼睛（Browser Use）

typecheck 能验类型、测试能验逻辑，但**"页面长得对不对"只有看到渲染结果才能回答**——面板被 z-index 盖住、暗色模式对比度塌掉，代码每一行都是"对"的。

三关能力（每解锁一种"看"的能力，多抓一类问题）：

1. **截图视觉验证**：抓布局、遮挡、配色。
2. **读页面结构**（可访问性树/DOM）：驱动交互——填表、点击，抓"有没有、能不能"。组合拳：结构负责交互，截图负责最终验收。
3. **主动造边界条件**：超长文本、暗色模式、窄屏视口、空数据——验收不能只覆盖 Happy Path。

### 工具选型：分清层级

- **驱动层（二选一）**：agent-browser（CLI + Skill，按需加载，几乎零常驻开销）vs Playwright MCP（工具 schema 启动即全量灌入上下文）。作者选 agent-browser。
- **排查层（按需）**：Chrome DevTools MCP——console 报错、network、性能 trace。
- **兜底**：Computer Use（原生对话框、桌面应用）。更慢更贵更易错，浏览器够得着的就不用它。

用独立 Chrome 实例（`--remote-debugging-port=9222 --user-data-dir=...`）维护登录态，不污染日常浏览器。CLAUDE.md 固化："UI 相关改动完成后必须打开页面截图自查，覆盖暗色模式和窄屏。"

## 4. 自然语言 UI 回归测试（Midscene）

传统 e2e 两个硬伤：选择器脆弱（重构就断）；`toBeVisible` 只查 DOM 可见性，**根本不管元素被不被盖住**。

Midscene.js（字节开源）把验收标准直接当测试跑：

```js
await aiTap('右上角的"更多筛选"按钮');
await aiAssert('"更多筛选"弹出的面板完整可见，没有被下方的表格卡片盖住');
```

没有选择器；集成 Playwright，报告带每一步截图和判断依据。三种用例形态：直接断言（含切视口/主题的造条件步骤）、先交互再断言（注意测试信号要选可靠的——弹窗卡着比"没有 toast"更稳）、瞬时 UI 用 `startObserving` 连续采样后断言。

经验：

- **AI 视觉断言的软肋是精确阈值**：对比度这种有数字定义的（WCAG ≥ 4.5:1）交给 axe-core 算，模糊观感交给模型，同一份 spec 各司其职。
- **成本**：每步都是视觉模型调用；开 cache 后规划/定位结果可复用，但断言永远不走缓存。
- **谁来写用例**：你出验收标准（自然语言），Coding Agent 直译成 aiTap/aiAssert。
- 测试反复报错时，先判断是页面真有问题还是用例写错了——需要人的判断力。

## 5. 回归测试平台

用例攒到几十上百条后，光靠一条命令不够。最小平台三件事：

1. **管用例**：cases.json 存分组/优先级元数据（P0 冒烟集每次提交必须绿）。
2. **管执行**：spawn playwright 子进程，`-g` 按分组过滤，轮询显示进度。
3. **管结果**：runs.json 留痕最近 50 轮，失败用例挂上 Midscene HTML 报告链接。

触发链路：统一成 `pnpm test:smoke` → Git pre-commit hook（Husky）或 Claude Code PreToolUse hook 拦提交（**二选一，别同时配，会重复跑**）。分工：本地平台给即时反馈，CI 全量回归当合并前最后一道闸门。

后续可加：失败自动重跑（滤偶发误判）、flaky 标记、按 git diff 选用例。
