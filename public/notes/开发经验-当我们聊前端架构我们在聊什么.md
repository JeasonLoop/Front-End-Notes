# 当我们聊前端架构，我们在聊什么

最近几年「前端架构」这个词提得越来越多，刚入行的朋友可能会觉得很虚，我聊聊我的理解。

## 架构不是凭空画出来的

我刚工作的时候以为架构就是画个框图，分分层，说说模块怎么拆分，然后就完事了。

实际不是。**好架构都是随着业务发展长出来的，不是一开始设计出来的**。

一开始业务不确定，你上来就搞个非常复杂的架构，过度设计，最后反而累死自己。

## 好架构解决什么问题

### 1. 解决复用问题

业务发展了，多个页面要用同一个组件，多个项目要用同一个工具，你得有地方放，方便引用，方便更新，这就是架构要解决的。

### 2. 控制复杂度

项目大了，几百个文件，上来一个新人，不知道从哪看。架构清晰，目录结构清楚，谁在哪干什么一目了然，新人能快速上手。

### 3. 方便协作

多人开发，你改你的模块，我改我的模块，不冲突，不互相影响，CI/CD 跑起来，上线不慌。

### 4. 应对变化

需求变是常态，架构要能接住变化，改一个功能不要动十个地方。

## 我理解的好架构标准

### 1. 清晰依赖

谁依赖谁，清清楚楚，不要循环依赖，不要双向依赖。A 能用 B，B 不能反过来依赖 A，分层就要遵守分层规则。

### 2. 高内聚低耦合

相关代码放一起，不相关的分开，改需求只需要改一个地方，不要到处撒牙签。

### 3. 够用就好，不要过度设计

你一个个人博客，两三个人开发，搞什么微前端、什么 Monorepo 复杂架构，纯纯浪费时间。能解决当前问题，留点扩展空间，就够了。

### 4. 性能达标

架构层面决定了很多性能问题，打包能不能拆分，首屏能不能懒加载，资源能不能缓存，这些都是架构要考虑的。

## 怎么提升架构能力

### 1. 多看好项目源码

去 GitHub 看优秀开源项目，看看人家目录怎么分，依赖怎么组织，为什么这么分，看多了你就有感觉了。

### 2. 重构，持续重构

代码坏味道出来了，就及时重构，不要堆着。重构一次，你对架构的理解就深一点。

### 3. 多踩坑

踩过坑你才知道为什么要这么设计，为什么不那么设计。没踩过坑，听别人说都是纸上谈兵。

## 最后

前端发展太快，今天新框架明天新概念，架构思想其实没变多少：**把复杂问题拆成简单问题，把代码组织好，让后人好维护**。

不用追求高大上的名词，能解决你现在问题的架构，就是好架构。
