# 认知重建：角色转变与幻觉控制

> 对应课程第一章。两件事：把派活的话说完整，把幻觉用工程手段压下去。

## 1. "一句话干活"为什么是谎言

"帮我重构一下这个模块，代码有点乱" → Agent 热火朝天改了十几个文件 → 上线两天生产报错：它把一段看着"冗余"的兼容逻辑优化掉了，而那段代码是给老用户数据特意留的。

本质：**你把一个需要大量上下文的任务，压缩成了一句没有任何上下文的话，然后期待对方完全懂你。**

一句话里缺的四样东西，没有一样是"话术"，全是信息：

| 缺的东西 | 说明 |
| --- | --- |
| 目标 | "代码有点乱" vs "理顺模块、方便下个月加多租户"，重构方向完全不同 |
| 边界 | 哪些文件能动、哪些绝对不能碰、对外接口要不要保持不变 |
| 历史包袱 | 为什么这里用怪写法、当年绕过了什么坑——只活在脑子里，Agent 读遍仓库也挖不出来 |
| 验收标准 | 改成什么样算完？不说它就自定最宽松标准，然后宣布完成 |

好的 prompt 就是把这些信息搬齐，再加一个刹车：

```
帮我重构 src/billing 这个模块。

背景：下个月要加多租户支持，先把结构理顺。

约束：
- 对外导出的接口签名保持不变，调用方不要动
- normalizeLegacyOrder 里的兼容逻辑不能删，那是给 2024 年之前注册的老用户留的
- 只动这个目录，别的地方不要碰

做完之后跑 pnpm test，把结果贴给我。
改动如果超过 10 个文件，先停下来跟我说一声。
```

有些信息是任务独有的（目标、这次的红线），每次现写；有些是项目级的（技术栈、测试命令、通用规范），沉淀到 Agent 每次开工自动读的地方——见 [上下文工程](./02-上下文工程-CLAUDEmd与会话管理.md)。

## 2. 角色转变：你是管理者，不是执行者

- 你不再是写代码的人，你是派活、给上下文、验收产出、把控方向的人。
- 传统训练只教"怎么把代码写好"，没教"怎么让别人把活干好"——而这恰恰是管 Agent 的核心。
- 不同任务管理力度不同：写类型定义、生成测试用例，一句话扔过去就行；跨模块架构迁移，决策权必须留在自己手里。
- **瓶颈通常是你自己**：上下文塞满无关信息、一个 prompt 干复杂任务、第一步走歪一路将错就错、从来不 review——喊"模型降智"的人全是管理动作缺失。

## 3. 幻觉的黄金原则：加中间层

先接受事实：**LLM 的幻觉数学上消除不掉**（OpenAI 论文《Why Language Models Hallucinate》：概率生成天然有随机性，且行业评测奖励"自信地猜"）。它永远不会以"我不太确定"的姿态出现。

计算机科学的老办法：不可靠的组件不靠把它做到完美，靠在外面包一层（内存加校验码、网络加 TCP、磁盘加 RAID）。

**给幻觉包一个 review 层**，算概率账：

- 单次正确率 90% → 一轮独立 review（90% 抓住率）→ 残留 1%
- 再叠一轮 → 0.1%；错误率指数衰减，成本只线性增加

### review 必须独立，否则白跑

同一个会话里说"你再检查一遍"基本无效：模型被自己的推理路径锚定了（ICLR 论文《LLMs Cannot Self-Correct Reasoning Yet》：无外部反馈的自我纠错性能不升反降）。

独立性的两个来源：

1. **干净的上下文**：开新会话（或派 subagent）只喂 git diff + 审查指令，让它看陌生人的代码。
2. **不同的模型**：Claude 写的让 GPT 挑刺，反之亦然——不同模型犯错位置不一样，一起看走眼的概率低得多。

审查关注点要**固化成 checklist**（安全漏洞、竞态、错误处理、性能、边界），沉淀成 review Skill，可自由组合新会话 / subagent / 换模型。作者案例：review Skill 一句话抓出"会话状态存实例本地内存，多实例部署会丢"——本地根本不复现的坑。

### 手动挡：苏格拉底式提问

关键产出验收前必问：

- "这个实现有什么安全风险？"
- "这个方案在什么情况下会失败？"
- "如果数据量增长 10 倍，这个设计还成立吗？"
- **"你漏掉了什么？"**——几乎零成本，命中率高得惊人（对抗 WYSIATI：模型永远给你看起来"完整"的输出）。

## Checklist

- [ ] 派活时四件套齐了：目标 / 边界 / 历史包袱 / 验收标准
- [ ] 大改动加了"刹车"（超 N 个文件先停下来说一声）
- [ ] 关键产出用独立上下文或换模型 review，而不是让它自己检查自己
- [ ] 验收前问过一句"你漏掉了什么？"
